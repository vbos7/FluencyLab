Tarefa 24 Pessoa A Pendente

Fundamentos do frontend e cliente de API

O backend está pronto, mas o frontend ainda mostra dados inventados — cada tela importa um arquivo de mock (frontend/app/_lib/practice.ts, ranking.ts etc.) em vez de chamar a API de verdade. Esta tarefa é a base de tudo que vem depois: configura o "telefone" entre o Next.js e o Laravel. Vale a pena todo mundo do time ler esta página, mesmo que só a Pessoa A vá implementá-la — os conceitos aqui valem para as tarefas 25 a 36 inteiras.

O que você vai aprender

  • A diferença entre Server Components e Client Components no Next.js — e por que isso muda como você busca dados.
  • Por que precisamos de duas formas diferentes de chamar a API (uma para cada tipo de componente).
  • Como guardar o token do Sanctum num cookie, para ele "viajar" tanto para o navegador quanto para o próprio servidor do Next.js.

Server Components vs Client Components — em termos simples

Repare como as páginas deste projeto já estão organizadas: app/(auth)/login/page.tsx é bem curta, só desenha um componente <LoginForm />. Quem realmente faz alguma coisa (guarda o que o usuário digitou, reage a cliques) é o LoginForm, que começa com "use client" no topo do arquivo.

Isso não é coincidência — é como o Next.js (a partir do "App Router", que é o que esse projeto usa) funciona por padrão:

  • Todo arquivo page.tsx é, por padrão, um Server Component. Ele roda no servidor, antes da página chegar no navegador do usuário. Não existe useState, não existe onClick, não existe window ou document aqui — porque não tem navegador nenhum rodando esse código, só o servidor do Next.js.
  • Um arquivo só vira Client Component se tiver "use client" na primeira linha. Aí sim ele roda no navegador, depois da página carregar, e pode usar useState, onClick, useEffect etc — exatamente como você já está acostumado nos componentes de formulário e botões deste projeto.
Por que essa separação existe? Pense assim: o Server Component já chega pronto, com o HTML montado — é mais rápido pra carregar e melhor pra SEO. O Client Component é necessário quando a tela precisa reagir a alguma coisa que só acontece depois que a página já carregou (digitar, clicar, etc). Um app real combina os dois: páginas de listagem geralmente são Server Components (buscam os dados e já entregam prontos); formulários e botões interativos são Client Components.

Por que isso muda como buscamos dados da API

Como Server Component roda no servidor (não no navegador), ele não tem acesso a localStorage nem a bibliotecas que dependem do navegador (como o js-cookie que vamos instalar). Mas ele consegue ler os cookies que o navegador mandou junto com a requisição, através de uma função especial do Next.js: cookies(), importada de next/headers.

Resultado prático: vamos ter dois jeitos de chamar a API, e cada tarefa vai te dizer qual usar:

  • Em Client Components (formulários, ações de clique — ex: login, submeter resposta): usamos uma instância do axios com um "interceptor" que pega o token do cookie via js-cookie e já anexa no header de toda requisição, automaticamente.
  • Em Server Components (páginas de listagem — ex: cursos, ranking): usamos a função nativa fetch do JavaScript, lendo o token manualmente via cookies() do Next.js antes de montar a requisição.

Por que cookie, e não localStorage puro? Porque um cookie criado no navegador é enviado automaticamente em toda requisição feita para o próprio Next.js — inclusive quando o Next.js está montando a próxima página no servidor. localStorage só existiria no navegador, e o Server Component nunca conseguiria enxergar o token.

Passo a passo

1

Instalar as dependências

Local, fora do Docker — o frontend roda direto com Node, não precisa entrar em container:

cd frontend
npm install axios js-cookie
npm install -D @types/js-cookie
2

Variável de ambiente

O endereço da API já está configurado no docker-compose.yml como NEXT_PUBLIC_API_URL=http://localhost:8000/api (o prefixo NEXT_PUBLIC_ é o que o Next.js exige para uma variável de ambiente ficar disponível tanto no servidor quanto no navegador). Pra rodar o frontend localmente fora do Docker durante o desenvolvimento (npm run dev), crie também:

frontend/.env.local
NEXT_PUBLIC_API_URL=http://localhost:8000/api

(esse arquivo já deve estar coberto pelo .gitignore padrão do Next.js — confira antes de commitar)

3

Cliente para Client Components

frontend/app/_lib/api.ts
"use client"

import axios from "axios"
import Cookies from "js-cookie"

export const apiClient = axios.create({
    baseURL: process.env.NEXT_PUBLIC_API_URL,
    headers: {
        Accept: "application/json",
    },
})

// Roda antes de TODA requisição feita com apiClient — se existir um
// token guardado no cookie, anexa no header Authorization automaticamente.
apiClient.interceptors.request.use((config) => {
    const token = Cookies.get("token")
    if (token) {
        config.headers.Authorization = `Bearer ${token}`
    }
    return config
})

A partir de agora, em qualquer Client Component, basta import { apiClient } from "@/app/_lib/api" e chamar apiClient.post("/login", {...}) — o token (quando existir) já vai junto, sem você precisar lembrar de adicionar o header toda vez.

4

Cliente para Server Components

frontend/app/_lib/server-api.ts
import { cookies } from "next/headers"

export async function fetchFromApi<T = unknown>(path: string): Promise<T> {
    const cookieStore = await cookies()
    const token = cookieStore.get("token")?.value

    const res = await fetch(`${process.env.NEXT_PUBLIC_API_URL}${path}`, {
        headers: {
            Accept: "application/json",
            ...(token ? { Authorization: `Bearer ${token}` } : {}),
        },
        cache: "no-store", // sempre busca dado novo, não usa cache do Next.js
    })

    if (!res.ok) {
        throw new Error(`Erro ao buscar ${path}: ${res.status}`)
    }

    return res.json()
}
cache: "no-store" Por padrão, o Next.js tenta cachear chamadas de fetch feitas em Server Components, pra acelerar páginas que não mudam com frequência. Como nossos dados mudam o tempo todo (XP, ranking, etc), desligamos esse cache explicitamente. Mais pra frente, se quiser otimizar uma rota específica que muda pouco (ex: lista de cursos), dá pra remover essa opção ali.

A partir de agora, em qualquer Server Component (ou seja, em qualquer page.tsx sem "use client"), você pode fazer:

export default async function CursosPage() {
    const courses = await fetchFromApi("/courses")
    // ...
}

Repare que a função do componente virou async — isso só é possível em Server Components. É o jeito do Next.js permitir "esperar" os dados chegarem antes de montar o HTML.

Como testar

Ainda não tem nenhuma tela usando isso — o teste real vem nas próximas tarefas. Mas dá pra confirmar que o setup está correto criando uma página de teste temporária:

// algum lugar temporário, ex: app/teste/page.tsx
import { fetchFromApi } from "@/app/_lib/server-api"

export default async function TestePage() {
    const courses = await fetchFromApi("/courses")
    return <pre>{JSON.stringify(courses, null, 2)}</pre>
}

Suba o frontend (npm run dev dentro de frontend/, ou via Docker) e acesse /teste — deve mostrar o JSON dos cursos que você cadastrou no backend (tarefa 07). Apague essa página de teste depois.
