Tabela de usuários + papel (role)

Essa tarefa já está implementada — leia esta página antes de partir pra tarefa 02, porque tudo que vem depois usa o que está descrito aqui.

O que já existe

  • Laravel 13 rodando em PHP 8.4 via Docker (docker compose up sobe tudo).
  • A tabela users padrão do Laravel (name, email, password) com uma coluna extra: role, que só pode ser "admin" ou "student", com "student" como valor padrão.
  • O pacote Laravel Sanctum instalado e configurado em modo token (Bearer) — explicado na página de Fundamentos.
  • Uma rota de exemplo já funcionando: GET /api/user, protegida por auth:sanctum.

Por que a coluna role existe desde já

Várias tarefas mais à frente (principalmente as de Admin, tarefas 21-23) precisam diferenciar um usuário comum de um administrador. Em vez de cada pessoa do time inventar sua própria forma de marcar isso depois, a coluna já nasceu pronta — assim todo mundo que referenciar $user->role está usando a mesma base.

backend/database/migrations/..._add_role_to_users_table.php
public function up(): void
{
    Schema::table('users', function (Blueprint $table) {
        $table->enum('role', ['admin', 'student'])->default('student')->after('password');
    });
}

Isso é uma migration — lembra do vocabulário da tarefa anterior? Ela não cria a tabela users do zero (essa já vem com o Laravel), só adiciona uma coluna numa tabela que já existe. Schema::table(...) ao invés de Schema::create(...) é o sinal disso: estamos alterando, não criando.

Como o Sanctum foi ligado ao usuário

O model User ganhou um "superpoder" (um trait, em PHP) que permite gerar e validar tokens:

backend/app/Models/User.php
use Laravel\Sanctum\HasApiTokens;

class User extends Authenticatable
{
    use HasApiTokens, HasFactory, Notifiable;
    // ...
}

É esse HasApiTokens que vai permitir, na tarefa 03, escrever algo como $user->createToken('token-de-login') pra gerar o "crachá" que o frontend vai guardar.

A rota de exemplo já registrada

backend/routes/api.php
Route::get('/user', function (Request $request) {
    return $request->user();
})->middleware('auth:sanctum');

Repare no ->middleware('auth:sanctum') no final — é exatamente o "porteiro" descrito na página de Fundamentos. Sem um token válido no header Authorization, essa rota nunca chega a executar a função: o middleware já barra antes e devolve um erro.

Testando o que já existe

Com os containers rodando (docker compose up -d), tente:

curl http://localhost:8000/api/user

Resposta esperada (sem token, então 401 — não autorizado):

{"message":"Unauthenticated."}

Isso confirma que o middleware está funcionando: ele bloqueou a requisição antes mesmo dela chegar perto do banco de dados.
