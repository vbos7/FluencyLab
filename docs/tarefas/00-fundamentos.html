Fundamentos — Do PHP puro ao Laravel

Você sabe pegar um formulário HTML, ler $_POST['email'], jogar isso direto numa query SQL e devolver alguma coisa na tela. Laravel faz exatamente a mesma coisa por baixo dos panos — só que organizada em pedaços com nomes diferentes. Esta página é o "dicionário de tradução" entre o que você já sabe e o vocabulário que vai aparecer em toda tarefa daqui pra frente.

1. De um arquivo único para Rota → Controller

Em PHP puro, um formulário de login provavelmente manda os dados pro próprio arquivo, ou pra outro .php que faz tudo:

login.php (PHP puro)
<?php
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $email = $_POST['email'];
    $senha = $_POST['senha'];

    $conn = mysqli_connect('localhost', 'root', '', 'meubanco');
    $sql = "SELECT * FROM usuarios WHERE email = '$email'";
    $result = mysqli_query($conn, $sql);
    $usuario = mysqli_fetch_assoc($result);

    if ($usuario && password_verify($senha, $usuario['senha'])) {
        echo json_encode(['sucesso' => true]);
    } else {
        echo json_encode(['sucesso' => false]);
    }
}

No Laravel, esse mesmo trabalho é dividido em duas peças:

  • Rota (routes/api.php): só diz "quando chegar um POST em /api/login, chama esse método". É o equivalente a você ter decidido "esse formulário manda pra login.php" — só que centralizado num arquivo só, em vez de espalhado em vários .php.
  • Controller: a classe PHP que efetivamente faz o trabalho (ler os dados, consultar o banco, devolver a resposta). É o conteúdo que estava dentro do if ($_SERVER['REQUEST_METHOD'] === 'POST') ali em cima, só que organizado num método de uma classe.
routes/web.php vs routes/api.php O Laravel já vem com dois arquivos de rota separados. web.php é pra quando o próprio Laravel devolve uma página HTML pronta (com Blade, o "PHP com templates" do framework) — não é o nosso caso, porque quem desenha a tela aqui é o Next.js. api.php é só pra respostas JSON, e tudo que você registrar lá já nasce com o prefixo /api/ na URL e passa pelo "crachá" do Sanctum (mais sobre isso já já). Conclusão prática: nas tarefas deste guia, você vai mexer quase sempre em routes/api.php.

2. De $_GET / $_POST para o objeto Request

Em vez de ler direto das variáveis globais $_GET/$_POST, o Laravel entrega pro seu Controller um objeto Request já pronto, com os dados do formulário/JSON dentro:

// PHP puro
$email = $_POST['email'];

// Laravel — o $request já chega pronto no método do Controller
$email = $request->input('email');
// ou, se você validou os campos antes (mais comum, ver tarefa 02):
$email = $request->validated()['email'];

A vantagem não é só sintática: o Request do Laravel já sabe ler tanto formulário tradicional quanto JSON (que é o que o Next.js vai mandar), então você não precisa se preocupar se o dado veio de $_POST ou de um body JSON — é sempre $request->input('campo').

3. De SQL na mão para Eloquent

Você já escreveu algo como:

$sql = "INSERT INTO usuarios (nome, email, senha) VALUES ('$nome', '$email', '$senhaHash')";
mysqli_query($conn, $sql);

O Eloquent (o ORM do Laravel — "ORM" = uma camada que transforma linhas de tabela em objetos PHP) faz a mesma coisa assim:

User::create([
    'name' => $nome,
    'email' => $email,
    'password' => $senhaHash,
]);

Repare: nenhum SQL escrito à mão, nenhum risco de SQL injection (o Eloquent já escapa os valores pra você), e User é só uma classe PHP que representa a tabela users — chamada de Model. Pra buscar um registro, em vez de SELECT * FROM usuarios WHERE id = 1, você escreve User::find(1).

4. De echo json_encode(...) para return response()->json(...)

// PHP puro
echo json_encode(['sucesso' => true, 'usuario' => $usuario]);

// Laravel
return response()->json(['sucesso' => true, 'usuario' => $usuario]);
// ou simplesmente devolver um array/Model direto — o Laravel converte pra JSON sozinho:
return $usuario;

Mesma ideia, só que o Laravel cuida de detalhes que você normalmente faria na mão (definir o header Content-Type: application/json, formatar erros de validação, etc).

5. De $_SESSION para token Sanctum

Em PHP puro com sessão tradicional, depois do login você faria:

session_start();
$_SESSION['usuario_id'] = $usuario['id'];
// nas páginas seguintes:
session_start();
if (!isset($_SESSION['usuario_id'])) { /* não logado */ }

Isso funciona porque o navegador guarda um cookie de sessão e o PHP "lembra" quem é você a cada requisição, no mesmo servidor.

Só que aqui o frontend (Next.js) e o backend (Laravel) são duas aplicações separadas, rodando em containers/portas diferentes. Não dá pra depender de sessão de servidor do mesmo jeito. O Sanctum resolve isso com um token: pense nele como um crachá de visitante.

  1. No login, o backend gera uma string aleatória (o token) e devolve pro frontend.
  2. O frontend guarda esse token e manda ele em todo request seguinte, num header: Authorization: Bearer <token>.
  3. O Laravel confere esse header antes de deixar a requisição chegar nas rotas protegidas — isso é o middleware auth:sanctum, que você vai ver em quase toda rota daqui pra frente.
Por que não usar sessão então? Dá pra usar Sanctum em "modo sessão" também (chamado de modo SPA), mas isso exige configurar cookies entre domínios diferentes com cuidado (CORS, same-site, etc). Como o frontend é uma aplicação separada, é mais simples — e é o que vamos usar neste projeto — trabalhar só com token (modo API), sem mexer em cookie nenhum.

6. Vocabulário rápido (cola pra consultar depois)

  • Migration: um arquivo PHP que descreve uma mudança na estrutura do banco (criar tabela, adicionar coluna). Rodar php artisan migrate aplica todas as migrations pendentes, em ordem — pense nisso como um "histórico de versões" da estrutura do banco.
  • Model: uma classe que representa uma tabela (ex: User → tabela users).
  • Eloquent: o nome do ORM do Laravel — o "tradutor" entre PHP e SQL.
  • Controller: a classe que recebe a requisição (depois de passar pela rota) e decide o que fazer.
  • Rota: a linha em routes/api.php que liga uma URL a um método de Controller.
  • Middleware: uma camada que intercepta a requisição antes dela chegar no Controller — usamos principalmente o auth:sanctum, que bloqueia quem não manda um token válido.
  • Form Request: uma classe dedicada só pra validar os dados de entrada (ex: "email é obrigatório e precisa ser um email válido"), em vez de validar com vários if dentro do Controller.
  • Seeder: um script que popula o banco com dados de teste/exemplo, pra você não precisar cadastrar tudo na mão toda vez que resetar o banco.
